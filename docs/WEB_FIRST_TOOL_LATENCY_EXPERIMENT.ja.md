# UAG Avatar Web: 初回ツール実行までの遅延実験

対象は独立した `uagav`（`awaku7/uag-web`）です。UAG 本体の `uagw` とは区別します。

## 目的

同じ LLM、同じプロンプト、同じローカル環境で `--room-workers 5` と `--room-workers 1` を比較し、ワーカー分離方式による入力から最初のツール実行開始までの遅延を確認します。

現行 `process_workers.py` では `--room-workers 2` 以上で入力ごとに `multiprocessing.get_context("spawn")` の子プロセスを生成し、`--room-workers 1` は同一プロセスのワーカー経路を使います。この比較は因果の候補を絞る診断であり、子プロセス起動時間そのものを計測するものではありません。

## 実験方法

1. ローカル PC の信頼できる `127.0.0.1` バインドで、まず `uagav --room-workers 5 --sandbox off` を起動します。リモート公開環境で Sandbox を無効化して実験しないでください。
2. ブラウザで `http://127.0.0.1:8000/?uag_latency=1` を開き、開発者ツールの Console を開いて `[uag-latency]` でフィルタします。画面遷移によってクエリ文字列が消えても、そのページを再読み込みしない限り計測は有効です。
3. ツール実行を必要とする同一のテキストプロンプトを、各設定で少なくとも5回送ります。初回と2回目以降の値を分けて記録してください。実行後はアイドル状態に戻ったことを確認してから次を送信します。
4. サーバーを停止し、`uagav --room-workers 1 --sandbox off` に切り替え、同じ操作を繰り返します。別のルーム・同じモデル・同じ推論設定を使用します。
5. それぞれの `first_work_tool` の中央値を比較します。最初のツールが `tool_catalog` や `tool_load` の場合は、`first_tool` と `first_work_tool` の両方を記録します。

| ログ項目 | 意味 |
| --- | --- |
| `queued` | Web から QUEUED 状態を最初に受信した時間 |
| `busy` | BUSY 状態を最初に受信した時間。LLM リクエスト開始時刻ではありません |
| `first_tool` | 最初の非空 `tool_activity` イベントを受信した時間（ツール探索を含む） |
| `first_work_tool` | `tool_catalog` / `tool_load` / `unload_tool` / `human_ask` を除いた最初のツール活動イベントを受信した時間 |
| `first_response` | 最初の Assistant 表示イベントを受信した時間 |

時間はブラウザ側の単調時計を基準とする経過ミリ秒です。ネットワークの往復、プロセス初期化、Context 構築、LLM 推論の合計を含み、各区間を独立に測定するものではありません。実際のツール内処理完了時間でもありません。

## 判定と次の一手

- **5 ワーカーだけ遅い**: 子プロセス起動・状態復元・初期化をサーバー側の詳細計測対象とします。ワーカー再利用は認証・ルーム・状態の分離を設計、検証してから着手します。
- **両方遅い**: Context 構築、LLM API、ツール探索の段階にサーバー側の計測点を追加します。
- **変動が大きい**: モデル・推論設定、履歴量、初回キャッシュ、同時実行状況を固定して再測定します。

`?uag_latency=1` がない通常表示では Console 計測ログは出しません。プロンプト、添付ファイル、セッション識別子はログ出力しません。ツール名のみ表示します。この段階ではバックエンドの挙動、ワーカー数のデフォルト値、Sandbox/認証設定、UAG 本体を変更しません。
